1. 数据爬取
docscrape爬取langchain文档，输出为markdown文件


2. 数据加载与文本块划分(TextChunking)
需求：md分布在根文件夹下，需要用递归加载，并且要保留langchain md文件的标题层次结构
使用DirectoryLoader + TextLoader加载文档，并用MarkdownHeaderTextSplitter保留标题层级，在标题边界处划分
Document对象：存储文档，优势是能保留元数据
由于MarkdownHeaderTextSplitter有时候会导致chunk过大，所以在内部嵌套RecursiveTextSplitter，将\n作为分隔符，最大token数量设为512，进行进一步切分。
属性
page_content：存储文本内容，字符串类型
Metadata：存储元数据，字典类型
Path对象：存储数据的路径

核心参数
PROJDCT_ROOT 根目录
DOCS_DIR 数据目录


3. 向量化(Embedding)
嵌入模型选择：
参数在1B及以下（本地训练）
重点关注Retrieval, rerank, 以及STS这三个指标
领域：Programming, Encylopaeidc以及written。其中programming最为契合，因为我做的是基于python包官方文档的知识问答，programming领域的嵌入模型天生契合我的主题。

reference : 
https://huggingface.co/IEITYuan/Yuan-embedding-2.0-en

4. 检索优化

(1) 查询字符串：用于进行语义检索
(2) 元数据过滤器: 从查询中提取出的结构化过滤条件

主要问题是
1. 中文查询的返回质量不佳
2. 部分问题真正包含答案的文档未进入top-30，重排无法生效

3. 将changelog/release降重，防止挤占其他文档。为了区分changelog以及release文档，增加元数据字段doc_type，具体规则实现位于src/ingestion/loader._parse_frontmatter函数中，加载完yamlfronter之后基于同类文档的共同特征设定规则，实现不同文档类型的区分并添加到文档元数据中，在之后的chunk切分模块自动继承。在重排模块设立惩罚项，如果chunk元数据有release/changelog标签，则直接扣分。后续考虑加入查询路由检验查询是否和changelog/release相关，并以此作为依据判断是否要执行惩罚项（如果相关，则不执行）

self-query评测（包含元数据过滤，由大模型判断）
基于之前检索评测的问题，已加入Python/JS判断字段，作为元数据过滤的基准之一
对于self-query的评测拆分为两部分
1. 问题拆解质量评测
2. 拆解（过滤）之后的检索效果

第一部分：问题拆解质量评测
原始查询重写（Self-Query Retriever）
从五个维度出发进行打分
忠实性：有没有加入原问题没有的意图、产品或约束
完整性：关键实体、产品名、版本、代码术语、否定条件是否保留
检索适配性：是否去掉了口语噪声，变成适合检索的表达
语言质量：中英文翻译是否准确
简洁性：是否引入无关扩展
为了实现原始查询重写的评测，在jsonl评测集中加入以下字段
1. must_keep_term : 原始查询中的关键字段，必须保留，用覆盖率衡量改写查询的完整性
2. rewrite_required : 0-1变量，人工判定该问题是否需要重写。用于检测大模型对于是否需要重写的判断能力。
至于其他指标，均由大模型自行衡量，而本项目负责设计一个结构化的提示词帮助大模型理解他的职责。
System Prompt：定义角色、评分维度、评分标准、输出 JSON 格式
User Prompt：填入当前样本的具体信息，让 LLM 针对这一条进行评分
根据第一轮检索测试的结果，中文query和英文文档的适配度存在问题，所以先对增加查询翻译功能。利用selfqueryretriever框架将提示词以及example作为参数导入即可。测试后发现

q057: rank 8 -> 2，这是因为本体是元数据过滤题
可以发现，目标页仍受 chunk 召回、Python/JS 双版本和标注粒度影响。

doc_type：明确命中 changelog、release notes、troubleshooting/排查/诊断、API reference、quickstart、明确的 tutorial 文档、release policy
排除条件：exclude/without/不要/排除/仅限/只看 且同时命中已知 metadata 目标

由此，我尝试通过以下优化方式解决
1. 优化检索，使用BM25 + dense向量融合的混合检索，考虑到其他评测题表现较好，权重分别设置为0.3, 0.7，仍然以稠密向量的语义匹配为主
2. chunk重构：增大candidate到40，不过度膨胀防止噪声过多。现做一遍粗排，选择rerank之后排名在15的chunk，然后做兄弟chunk合并，将同parent_id的兄弟子块合并，再做一次精排rerank，最后返回top chunk。

2. q001和q010仍然师表
3. 新增q019失败，原因是兄弟块合并之后对语义有稀释作用，最后一次的精排倾向于将正确答案往后排
调整策略
1. 最终精排池同时保留合并后的父块和原始命中的chunk
2. 让reranker自己选择合适的精度（父块或者其中的子块）
