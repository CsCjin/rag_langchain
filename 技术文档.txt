环境管理：利用uv进行虚拟环境管理（纯python项目，因此不考虑conda）


1. 数据爬取
docscrape爬取langchain文档，输出为markdown文件


2. 数据加载与文本块划分(TextChunking)
需求：md分布在根文件夹下，需要用递归加载，并且要保留langchain md文件的标题层次结构
使用DirectoryLoader + TextLoader加载文档，并用MarkdownHeaderTextSplitter保留标题层级，在标题边界处划分
Document对象：存储文档，优势是能保留元数据
由于MarkdownHeaderTextSplitter有时候会导致chunk过大，所以在内部嵌套RecursiveTextSplitter，将\n作为分隔符，最大token数量设为512，进行进一步切分。
属性
page_content：存储文本内容，字符串类型
Metadata：存储元数据，字典类型
Path对象：存储数据的路径

核心参数
PROJDCT_ROOT 根目录
DOCS_DIR 数据目录


3. 向量化(Embedding)
嵌入模型选择：
参数在1B及以下（本地训练）
重点关注Retrieval, rerank, 以及STS这三个指标
领域：Programming, Encylopaeidc以及written。其中programming最为契合，因为我做的是基于python包官方文档的知识问答，programming领域的嵌入模型天生契合我的主题。
选择IEITYuan/Yuan-embedding-2.0-en
reference : 
https://huggingface.co/IEITYuan/Yuan-embedding-2.0-en

先用Chroma（相较于Faiss，天然适配元数据的预过滤，也是该项目后续要使用的方法）向量库，如果后续不够用考虑替换Milvus（44158的数据量可能也不需要Milvus这种企业级的大数据库）

向量嵌入模型使用cuda进行加速（开发设备有独立显卡，型号为laptop5060）


4. 检索优化
由于langchain以小标题为块切分内容，所以天生适合利用元数据过滤数据，然后进行进一步的检索

5. 查询构筑
使用langchain架构中的Self_Query Retriever构筑，向LLM清晰传递文档内容以及其元数据，然后每当用户输入一个自然语言查询的时候，自查询检索器调用LLM，将查询分解为两部分：
(1) 查询字符串：用于进行语义检索
(2) 元数据过滤器: 从查询中提取出的结构化过滤条件

6. 问答链建设
RAGResponse类 : 用于定义rag的回复
RAGChain类 : 用于定义rag的框架
retriever : 查询重写并执行检索
answer_chain : 利用LCEL表达式构筑rag链条

7. 问答系统构筑
基于argparse包解析命令栏参数

1. 检索评测：评测rag系统返回chunk的性能
做截断评测，找到最适合返回检索的数量
计算指标：
Hit@k：top-k 中至少命中 1 个相关页面的问题比例
Recall@k：每个问题命中的相关 URL 数 / 标注相关 URL 总数，再平均
MRR@k：第一个相关页面排名倒数的平均值；k 内没命中记 0
nDCG@k	：按排名位置折损的相关性得分，再用理想排序归一化
结果分析：
1. 命中平均排名为2.46，且只有不到一半的命中排在前10，top-1精度不足
2. 根据分组分析的结果，how_to类型的问题表现良好，conceptual表现最差。
3. 元数据过滤题，不经过self-query相比其他普通题，表现较差，后续可以通过self-query的测试结果做进一步的验证
4. 本项目用了英文的嵌入模型，中文问题的召回表现不及英文

重排序实现
使用cross-encoder实现重排
code/model/cross_encoder.py实现模型的实例化
code/core/retriever.py调用cross-encoder模型，基于相关性得分实现重排序
cross-encoder模型使用BAAI/bge-reranker-base，轻量级模型部署较快
第一次召回candidate = 30，最终选择4个排名最高的相关文档
测试结果：
advantage
hit@1和hit@3显著上升，说明重排确实有利于将最相关的文档放置到前列的位置，保证了最相关的检索结果不被淹没在文档中间造成lost-in-middle问题
q020, q038, q061从原来的未命中/相关文档排名第8，优化为现在的首位命中
q016直接相关文档从第9升至第2
q004从第六升到第2
q005从第七升到第4
disadvantage
但我发现有新增了几条失败案例
主要问题是
1. 中文查询的返回质量不佳
2. 部分问题真正包含答案的文档未进入top-30，重排无法生效
3. 目标文档常常被release界面和changelog界面（版本发布说明以及更新日志）挤占，这类文档很长且包含很多的产品/主题，关键词密度极高。 
解决方案
1. BAAI/bge-reranker-base改用bge-reranker-v2-m3，更适合中文查询
2. 将candidate 从 30调整为50，确保最相关的文档能进入候选
3. 将changelog/release降重，防止挤占其他文档。为了区分changelog以及release文档，增加元数据字段doc_type，具体规则实现位于src/ingestion/loader._parse_frontmatter函数中，加载完yamlfronter之后基于同类文档的共同特征设定规则，实现不同文档类型的区分并添加到文档元数据中，在之后的chunk切分模块自动继承。在重排模块设立惩罚项，如果chunk元数据有release/changelog标签，则直接扣分。后续考虑加入查询路由检验查询是否和changelog/release相关，并以此作为依据判断是否要执行惩罚项（如果相关，则不执行）
测试结果
1. 改用模型之后，中文问题的hit@5从0.77升至0.86，MRR@5从 0.5690 提升到 0.7347。总体表现Hit@5 从 0.8246 提升到 0.9123，Hit@10 从 0.8596 提升到 0.9474，其中英文Hit@5 = 1.0000。但其中q001、q026、q044没有改善（修改前后始终未命中），q010和q057从未命中到进入前10，但依旧未进入top5。q001和q004的问题是被release, quickstart等页面挤占，q026和q057是元数据过滤题可以先不管。q010的问题是多重因素叠加：(1) 检索偏好subgraphs因为其中确实多次提到了关键词"subagents多次调用"，与问题中的"subagents重复请求"匹配度十分高，但确实不是我们需要的文档 (2)  中文跨语言匹配能力弱，将query重写为英文之后，目标也从rank9提升到rank4 (3) python/javascript双版本重复，python/multi-agents页面被同名但隶属于javascripts之下的文档挤占，后续可以考虑添加oss-python/oss-javascript字段进行解决
2. 将candidate转化为50之后，对比candidate=30的版本，召回指标没有增益。所以还是保留candiate=30，退回更改
3. 增加惩罚项之后，Hit@5 不变，但 top-1、MRR、nDCG 小幅改善。q001的目标文档从rank5提升到rank4, changelog文档被挤出前五。但是q001的top-5仍然有三个release页面，说明惩罚项对于release界面的约束不足，对changelog起到了一定的约束作用。
